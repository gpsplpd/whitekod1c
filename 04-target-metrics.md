# Целевые метрики качества — `ЦелевыеМетрики` (Q12)

Артефакт этапа 1, используется на этапах 2, 3 и 9. **Единственная точка хранения значений**: в коде — макет/константа `ЦелевыеМетрики`, в документах — этот файл. В остальных местах (промпт, тест-план, матрица моделей) на цифры ссылаются, но не дублируют их — иначе при согласовании новых порогов половина документации остаётся со старыми.

Статус: **предложение команды, требует подтверждения заказчиком** (Q12).

---

## 1. Метрики точности извлечения

Считаются по тест-набору `06-test-set.csv` после нормализации (`03-normalization-rules.md`).

| Поле | Целевое значение | Что считается «попаданием» |
|---|---|---|
| `наименование` | ≥ 90 % | Совпадает после нормализации (ВРЕГ, сжатые пробелы, без хвостовой пунктуации). Перестановка слов — не попадание |
| `цена` | ≥ 90 % | Числовое равенство после нормализации. Расхождение в 1 копейку — попадание; в 100 раз — нет |
| `единица_измерения` | ≥ 85 % | Совпадает каноническое значение |
| `кратность_упаковки` | ≥ 85 % | Совпадает число, либо оба значения `null` |
| `артикул` | ≥ 80 % | Совпадает после нормализации (включая «жёсткий» ключ). Пониженный порог — следствие грязных данных: артикул чаще всего искажается (`O`/`0`, `-`/`.`), и часть таких случаев уходит оператору |
| `примечание` | не нормируется | Проверяется выборочно: критично, чтобы в примечание не уезжала цена или артикул |

## 2. Метрики процесса

| Метрика | Целевое значение | Зачем |
|---|---|---|
| Доля строк `ТребуетВнимания` | ≤ 30 % | Выше — оператор тратит больше времени, чем при ручном вводе, смысл модуля исчезает |
| Доля строк `Ошибка` | ≤ 5 % | Выше — проблема в интеграции, а не в качестве модели |
| Доля строк, где оператор **исправил** хотя бы одно поле | ≤ 20 % | Прямая метрика полезности: кейс говорит про 3–4 часа ручной работы |
| Время обработки 400 строк | ≤ 15 мин | Требование к асинхронности и лимитам провайдера |
| Стоимость 400 строк | в пределах бюджета Q8 | Считается по формуле этапа 2 |

## 3. Метрика few-shot (этап 7)

| Гипотеза | Как проверяется | Критерий успеха |
|---|---|---|
| Подмешивание 1–3 примеров снижает долю правок | Прогон тест-набора без few-shot и с few-shot, сравнение доли исправленных полей | Снижение доли правок не менее чем на 3 п.п. по `наименование` |
| Примеры по «своему» поставщику лучше случайных | Прогон с примерами своего поставщика и с чужими | Свои — не хуже |

Если гипотеза не подтверждается — few-shot остаётся включённым только как демонстрация механики (требование кейса), а в отчёте фиксируется фактический результат, а не ожидаемый.

## 4. Правила измерения

1. Метрики считаются только по строкам, которые **были отправлены** в LLM (`Пропущена` в знаменатель не входит).
2. `ТребуетВнимания` входит в знаменатель точности — «сомнительная» строка, которую оператор не поправил, всё равно считается ошибкой, если поле не совпало с эталоном.
3. Каждый прогон фиксируется в протоколе (`05-usecases-and-testplan.md`, §4): модель, версия промпта, версия схемы, версия правил нормализации, дата, число строк.
4. Сравнивать модели и версии промпта можно только на одном и том же тест-наборе и одной версии правил нормализации.

## 5. Что делать при недостижении порогов

| Ситуация | Действие |
|---|---|
| Провал по `наименование` | Проверить MECE-правила в промпте (не остаётся ли артикул внутри наименования), добавить few-shot по проблемному поставщику |
| Провал по `цена` | Проверить обработку диапазонов и пометок НДС; чаще всего виновата не модель, а нормализация |
| Провал по `артикул` | Проверить шаг `O`→`0` и сохранение дефисов; не «улучшать» промпт, а править правила нормализации |
| Слишком высокая доля `ТребуетВнимания` | Ослабить «мягкие» проверки (например, разрешить `null` в единице без понижения статуса) — но только с согласия заказчика |
| Все метрики хорошие на тест-наборе, плохие на реальном файле | Тест-набор синтетический; запросить реальные прайсы (этап 1, правка 4) |
